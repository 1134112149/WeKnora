# 课题三：评测任务持久化

## 一句话说明

本次改动解决了一个明确的工程问题：评测任务原来只保存在应用进程内存中，服务重启后无法继续查询；现在评测任务、进度、指标和失败信息会写入数据库，重启服务后仍可通过原接口查询。

## 为什么选择这个点

- **可实现**：不改变评测接口和核心评测流程，只增加持久化层，适合短周期交付。
- **可展示**：可以现场创建评测任务、看到状态变化，再重启服务查询同一个任务。
- **有实际价值**：长评测任务不会因为容器重启而丢失结果，便于后续任务列表、历史追踪和失败恢复。
- **风险可控**：用户原有知识库不被评测流程清理，数据库迁移同时覆盖 PostgreSQL 和 SQLite。

## 实现内容

新增 `evaluation_tasks` 表，保存以下信息：

| 字段 | 用途 |
| --- | --- |
| `id` | 评测任务 ID |
| `tenant_id` | 租户隔离 |
| `dataset_id` | 数据集 ID |
| `status` | 待运行、运行中、成功、失败 |
| `total` / `finished` | 评测进度 |
| `params_json` | 评测参数 |
| `metric_json` | 检索和生成指标 |
| `err_msg` | 失败原因 |

服务行为如下：

1. 创建评测任务时立即落库。
2. 任务开始、进度更新、成功或失败时更新数据库。
3. 查询接口优先读取内存；内存没有任务时自动回查数据库。
4. 查询仍校验租户 ID，避免跨租户读取任务。

## 演示流程

1. 启动 WeKnora，打开评测页面或调用 `POST /api/v1/evaluation`。
2. 记录返回的 `task_id`，轮询 `GET /api/v1/evaluation?task_id=...`。
3. 展示状态从运行中变为成功，并展示 `total`、`finished` 和指标。
4. 重启 `app` 容器。
5. 再次查询同一个 `task_id`，证明结果来自数据库而不是进程内存。
